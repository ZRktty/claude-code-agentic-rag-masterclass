# 3. Chat Core

🔴 **Complex** - streaming proxy + newer OpenAI API surface + full-stack coordination. If it proves too large for one sitting, split into 3a (backend thread + streaming routes) and 3b (frontend chat UI) — the two halves are separable once the request/response and SSE event contracts are fixed.

## Scope

Thread CRUD endpoints, OpenAI Responses API integration (conversation creation, sending messages, SSE streaming proxy), and the chat UI (thread sidebar, message view, streaming render).

**Not in scope**: file attach, file_search, LangSmith (sub-plan 4) — but structure the OpenAI client as a single import point (`backend/src/lib/openai.ts`) so sub-plan 4 can wrap it with `wrapOpenAI` as a one-line change.

## ⚠️ Standing risk for this whole sub-plan

The OpenAI Responses/Conversations API method names and the streaming event taxonomy are the single biggest accuracy risk in this plan. **Verify exact method names, parameter shapes, and streaming event names against the installed `openai` npm package's TypeScript types at implementation time** — do not trust names written below, which may have drifted.

## Tasks

1. **OpenAI client** — `backend/src/lib/openai.ts`: `export const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY })`.
   - **Validate**: smoke script calling `openai.models.list()` returns a non-empty array (proves the API key is valid before building on top of it).

2. **Thread CRUD routes** — `backend/src/routes/threads.ts`, mounted at `/api/threads`:
   - `POST /api/threads` `{ title? }` → `openai.conversations.create({})` (verify exact current SDK method name/shape) → insert row via the user-scoped client from sub-plan 2 → return the row.
   - `GET /api/threads` → list, RLS-scoped, ordered `updated_at desc`.
   - `GET /api/threads/:id` → single row (404 on not-found/not-owned — indistinguishable by design, which is the correct/safe behavior).
   - `PATCH /api/threads/:id` → rename.
   - `DELETE /api/threads/:id` → delete row; also attempt `openai.conversations.delete(id)` wrapped in try/catch so an OpenAI-side failure doesn't block the local delete.
   - **Validate**: curl each with a real bearer token obtained via the sign-in flow; confirm 201/200/404 as appropriate; **create a second test user and confirm their `GET /api/threads` does not include the first user's threads** — this is the RLS proof deferred from sub-plan 2.

3. **Message send + SSE streaming** — `POST /api/threads/:id/messages` `{ content }`:
   - Look up thread (RLS-scoped, 404 guard) for `openai_conversation_id`.
   - `openai.responses.create({ model, input: content, conversation: threadRow.openai_conversation_id, stream: true })` — verify the exact parameter name for attaching an existing conversation against the installed SDK's types.
   - Stream via Hono's SSE helper (`import { streamSSE } from 'hono/streaming'` — confirm current import path/API against the installed Hono version), forwarding at minimum `response.output_text.delta` (incremental text) and a terminal completion event, plus an `event: error` frame on failure. Event type names have shifted across OpenAI API versions — check the `openai` package's `ResponseStreamEvent` union type rather than assuming.
   - On success, patch `threads.updated_at` (and auto-title from the first message if still "New chat").
   - **Validate**: `curl -N -H "Authorization: Bearer $TOKEN" -d '{"content":"..."}' localhost:3001/api/threads/<id>/messages` shows `data:` lines arriving incrementally, not all at once; confirm the conversation now contains both messages via task 4's endpoint.

4. **Conversation history endpoint** — `GET /api/threads/:id/messages`: `openai.conversations.items.list(openai_conversation_id, { limit, order })` (verify current method name/shape), mapped to `{ id, role, content, createdAt }[]`.
   - **Validate**: after task 3's curl test, this endpoint returns both the user message and the assistant's reply in order.

5. **Mount + CORS** — `app.route('/api/threads', threadsRouter)` in `backend/src/index.ts`; confirm `cors()` allows the `Authorization` header from `http://localhost:5173`.
   - **Validate**: a browser fetch from the frontend dev server to the backend succeeds with no CORS console error.

6. **Frontend thread sidebar** — `frontend/src/features/chat/ThreadSidebar.tsx`, `useThreads.ts` hook, plus `frontend/src/lib/api.ts` fetch wrapper injecting `Authorization: Bearer ${session.access_token}`.
   - **Validate**: click "New thread," confirm it appears in the sidebar and survives a page refresh.

7. **Frontend message view + streaming input** — `MessageList.tsx`, `MessageInput.tsx`, `useChatStream.ts`. Consume SSE via `fetch` + `ReadableStream` reader (**not** the native `EventSource` API — `EventSource` can't send the bearer-token header or a POST body, so hand-roll SSE parsing over `fetch`'s streaming body).
   - **Validate**: send a message, watch the reply render token-by-token; reload mid-conversation and confirm history reloads via task 4's endpoint and matches what was streamed.

8. **Routing** — chat shell at `/` (sidebar + selected thread) and `/threads/:id` for direct linking.
   - **Validate**: navigate directly to a `/threads/<id>` URL and confirm it loads that thread's history without going through the sidebar.

9. **Error/loading states** — disabled input while streaming, visible error banner on network failure, empty state when no threads exist.
   - **Validate**: kill the backend mid-session, attempt to send a message, confirm a visible error appears rather than a silent hang.

## Risks to flag

- OpenAI Responses/Conversations API method names and streaming event taxonomy — verify against installed `openai` package types at implementation time.
- Model name should come from `OPENAI_MODEL` env var, not be hardcoded.
