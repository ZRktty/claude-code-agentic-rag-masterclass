# 4. File Attach + Observability

⚠️ **Medium** - well-scoped, but vector-store API shape and LangSmith-wrapping-a-streaming-call are both worth double-checking.

## Scope

Per-thread file attach (OpenAI Files API + OpenAI-hosted vector store) wired into `file_search`, plus LangSmith `wrapOpenAI` instrumentation and an end-to-end trace verification pass.

**Explicitly out of scope**: any custom chunking/embedding, pgvector storage, ingestion UI/route, or multi-file management beyond one attach affordance per thread — all Module 2.

## Tasks

1. **Migration** — `supabase/migrations/<ts>_add_thread_files.sql`:
   ```sql
   alter table public.threads add column if not exists openai_vector_store_id text;

   create table if not exists public.thread_files (
     id uuid primary key default gen_random_uuid(),
     thread_id uuid not null references public.threads(id) on delete cascade,
     user_id uuid not null references auth.users(id) on delete cascade,
     openai_file_id text not null,
     filename text not null,
     created_at timestamptz not null default now()
   );
   alter table public.thread_files enable row level security;
   create policy "Users can view own thread files" on public.thread_files
     for select using (auth.uid() = user_id);
   create policy "Users can insert own thread files" on public.thread_files
     for insert with check (auth.uid() = user_id);
   create index if not exists thread_files_thread_id_idx on public.thread_files(thread_id);
   ```
   - **Validate**: `select * from pg_policies where tablename = 'thread_files';` returns 2 rows; cross-user select test on another user's file row returns nothing.

2. **LangSmith wrapping** — `backend/src/lib/openai.ts`:
   ```ts
   import { wrapOpenAI } from "langsmith/wrappers";
   export const openai = wrapOpenAI(new OpenAI({ apiKey: process.env.OPENAI_API_KEY }));
   ```
   `bun add langsmith` in `backend/`. Env vars `LANGSMITH_TRACING=true`, `LANGSMITH_API_KEY`, `LANGSMITH_PROJECT` already in `.env.example` from sub-plan 1 — verify these are the current env var names, since LangChain/LangSmith has historically renamed `LANGCHAIN_*` → `LANGSMITH_*`.
   - **Validate**: send a chat message through the sub-plan-3 endpoint, then confirm a new trace appears in the LangSmith dashboard for the configured project; specifically confirm streaming still works after wrapping — verify `wrapOpenAI` supports the `responses.create({ stream: true })` call shape in the currently installed `langsmith` package version.

3. **File upload endpoint** — `POST /api/threads/:id/files` (multipart/form-data):
   - Verify thread ownership (RLS-scoped client).
   - `openai.files.create({ file, purpose: 'assistants' })` — verify current `purpose` value for `file_search` usage against current docs.
   - If `threads.openai_vector_store_id` is null: `openai.vectorStores.create({ name: \`thread-${threadId}\` })`, persist the id; else reuse.
   - Attach file to store, waiting for `completed` status before responding — use the SDK's upload-and-poll convenience method (verify current exact method name/casing, e.g. something like `openai.vectorStores.files.uploadAndPoll(...)` or `.createAndPoll(...)`).
   - Insert `thread_files` row, return `{ fileId, vectorStoreId, filename }`.
   - Note: this design uses **one vector store per thread by construction**, which naturally satisfies any per-call vector-store-count limit the Responses API's `file_search` tool may still carry over from the Assistants API — confirm current limits in docs regardless.
   - **Validate**: `curl -X POST -H "Authorization: Bearer $TOKEN" -F "file=@./test.pdf" localhost:3001/api/threads/<id>/files` → 201; confirm in the OpenAI dashboard (Storage → Vector stores) that a store exists containing the file with status "completed."

4. **Wire `file_search` into message send** — modify sub-plan 3's `POST /api/threads/:id/messages`: if `openai_vector_store_id` is present, pass `tools: [{ type: 'file_search', vector_store_ids: [openai_vector_store_id] }]` to `responses.create`; omit `tools` entirely otherwise.
   - **Validate**: attach a `.txt` file containing an obscure fact not in the model's training data, ask a question about it, confirm the streamed answer is correct **and** inspect the raw SSE output for `file_search_call` tool-use events as proof retrieval actually happened (not a hallucination).

5. **Frontend file attach control** — `FileAttach.tsx` inside `MessageInput`: paperclip button → file picker → multipart POST → progress spinner → "attached: filename" chip. Add `GET /api/threads/:id/files` (or fold into the thread-get response) so the chip persists across reloads, not just local component state.
   - **Validate**: attach a file, confirm the chip; reload the page/reselect the thread, confirm the chip still shows; ask a file-grounded question and confirm the reply reflects the file's content.

6. **End-to-end trace verification pass** — walk the full journey (sign up → sign in → new thread → plain message → attach file → file-grounded message) and confirm: (a) LangSmith shows a trace per OpenAI call, ideally tagged with `{ metadata: { threadId, userId } }` per call for debuggability; (b) no secrets/tokens leak into trace payloads; (c) streaming latency isn't visibly degraded by the wrapper.
   - **Validate**: manual review of a LangSmith trace's input/output panels; note findings in PROGRESS.md.

7. **Doc close-out** — confirm CLAUDE.md's Python/Pydantic references stayed fixed (double-check at the module boundary), mark PROGRESS.md's Module 1 section complete, and confirm PRD.md's existing "Module 1 → Module 2 Transition" section reads sensibly as the next step — **do not act on the Option A/B decision itself**, that's explicitly Module 2 scope.

## Risks to flag

- Files API `purpose` value and vector-store method names/casing are the main API-surface risks here — verify against the installed `openai` package's types before implementing.
- LangSmith env var naming (`LANGSMITH_*` vs. any legacy `LANGCHAIN_*` fallback) and streaming-wrap support should be confirmed against the current `langsmith` npm package README/changelog.
